# RCON Warfare — диспетчерская боевой техники для Minecraft

Управление боевой техникой (самолёты, вертолёты, БПЛА, танки) на сервере
Minecraft через RCON: тактическая карта со сканом рельефа, планировщик
маршрутов с действиями в точках, боты с собственными маршрутами, оружие
с боезапасом и топливом.

Проект — полный перезапуск наброска v10. Дефекты наброска разобраны в
[`BUGS.md`](BUGS.md), история — в [`CHANGELOG.md`](CHANGELOG.md),
накопленные знания о Minecraft/RCON — в [`SKILL.md`](SKILL.md).

В **v15** по ревью заказчика: интерфейс без верхней полосы с компактной
левой панелью объекта и хотбаром-иконками, запуск пресетами с модальным
редактором (drag&drop вооружения), экономика баз со снабжением авианосца
транспортником, разрушения с обломками/кратером/огнём, честная коллизия
наземной техники с приоритетом дорог, очки/звания/достижения оператора.

**Целевая версия сервера: Minecraft 1.20.1+ (vanilla).** Поддержка 1.21.2+
(новый синтаксис NBT) заложена через диалекты; определяется автоматически
зондами при подключении.

## Подключение к настоящему серверу

В `server.properties`:

```properties
enable-rcon=true
rcon.port=25575
rcon.password=ваш_пароль
```

Затем:

```bash
python main.py --probe --host 127.0.0.1 --port 25575 --password 2203
```

Настройки сохраняются в `bomber.json` (создаётся при первом сохранении) и
переопределяются переменными окружения `BOMBER_HOST`, `BOMBER_PORT`,
`BOMBER_PASSWORD`, `BOMBER_MOCK`, `BOMBER_TICK`.

### Правила, которые нельзя нарушать

1. **Ядро не знает про Qt.** Общение только через `EventBus`. Мутация виджетов
   из фоновых потоков запрещена (это дефект UI-01 в наброске).
2. **Ничего не уходит на сервер из GUI-потока.** Только `CommandQueue` или
   фоновый воркер. Иначе интерфейс замерзает на время RTT (RCON-06).
3. **`snapshot()` возвращает копии.** UI может перебирать снимок, пока физика
   меняет объекты (WORLD-02).
4. **Команды Minecraft строятся в `mc.py` и возвращают строку.** Это позволяет
   тестировать их сравнением строк, без сервера.
5. **Идентификатор юнита присваивается синхронно, до запуска потока** (UI-02).
6. **Каждый фикс сопровождается тестом.** Без теста статус в `BUGS.md` не
   меняется на `✅ исправлено`.

### Поток данных

```
        Minecraft-сервер
              ↑ ↓  RCON (пул соединений, пакетная отправка)
        CommandQueue ← приоритеты: CRITICAL / NORMAL / VISUAL(слияние)
              ↑
   ┌──────────┴───────────┐
   │  World (состояние)   │ ← PlayerTracker, TerrainScanner
   └──────────┬───────────┘
              ↑ snapshot() (копии, под локом)
     Units ⇄ Routes ⇄ AI          EventBus ──→ UI (Qt-поток через Signal)
              ↓
        MapRenderer → примитивы → QGraphicsScene
```

## Ключевые инженерные решения

### 1. Модель техники — блоки (решение заказчика)

Рассматривались два подхода:

| | Блоки (`setblock`) | Display-сущности (1.19.4+) |
|---|---|---|
| Команд на кадр | ~2 × N_блоков | 1 `tp` |
| Разрушает ландшафт | риск (см. ниже) | нет |
| Вид в мире | «настоящая» конструкция из блоков | блоки, парящие в воздухе |
| Совместимость | любая версия | 1.19.4+ |

Выбран **блочный** — как в исходном проекте. Возможности сервера всё равно
определяются зондом (`ServerCaps.model_backend`), поэтому при желании стратегию
можно заменить, не переписывая юниты: модель изолирована в `model.py`.

Набросок рисовал технику блоками так, что это ломало мир: `clear_model()`
вызывался для НОВОЙ позиции (старая не убиралась → след из блоков через всю
карту), а вокруг модели выполнялся `fill x±6 y-2..y+3 z±6 air replace`,
стиравший ландшафт и постройки в объёме 13×6×13 каждый тик. Как это решено —
в разделе 5.

### 2. Сканер рельефа — пакетное зондирование по уровням

Вместо 56 последовательных запросов на колонку — одна высота опрашивается сразу
у всех колонок одним `run_many`. Число сетевых заходов перестаёт зависеть от
числа колонок.

Замер (имитатор, localhost):

| Область | Колонок | Команд | Сетевых заходов | Время |
|---------|:-------:|:------:|:---------------:|:-----:|
| r=96, шаг 8 | 625 | ~10 000 | ~90 | 0.2 с |
| r=128, шаг 8 | 1 089 | 17 239 | 144 | 0.3 с |
| r=256, шаг 8 | 4 225 | 67 645 | **544** | **1.3 с** |

Набросок на той же области r=256/шаг 8 потребовал бы ~279 000 сетевых заходов
(4225 колонок × ~66 запросов). Пакетная отправка команд отдельно даёт 3.7×
на localhost (`python main.py --mock --bench`) и на порядок больше на
удалённом сервере, где выигрывается RTT.

Многопоточность не используется намеренно: сервер исполняет команды в одном
потоке, параллельные соединения дают только гонки (SCAN-02).

### 3. Определение версии — зондами, а не строкой

У vanilla нет команды `version`. Вместо парсинга строки проверяем возможности:
неизвестный тип сущности или команда дают `Unknown or incomplete command`,
известные — `Test failed` / `No entity was found`. Зонды не имеют побочных
эффектов (пустая выборка по несуществующему тегу), это проверяется тестом.

### 4. Очередь команд с приоритетами и слиянием

| Приоритет | Содержимое | При перегрузке |
|-----------|-----------|----------------|
| CRITICAL (0) | взрывы, спавн, удаление юнита | не выбрасывается |
| NORMAL (10) | выстрелы, tp, служебное | не выбрасывается |
| VISUAL (20) | кадры модели | сливается по ключу, выбрасывается первым |

Плюс rate-limit (по умолчанию 250 команд/с), чтобы не положить сервер.

### 5. Модель из блоков — с учётом каждого своего блока

По выбору заказчика техника рисуется блоками, а не display-сущностями. Чтобы
это не уничтожало мир и не грузило сервер, модель:

* описана декларативно (клетки `fwd/right/up/block`), углы применяются при
  проекции — один чертёж корректен под любым yaw/pitch/roll;
* **помнит каждый поставленный ею блок** и убирает только свои: никакого
  `fill ... air` по чужому ландшафту;
* обновляется **диффом**: на кадр уходят только изменившиеся клетки, повтор
  той же позы — ноль команд;
* рисуется не чаще `model_update_hz` (по умолчанию 5 Гц).

Бюджет: `2 × N_блоков × model_update_hz` команд/с на движущийся юнит.
Су-25 (22 блока) при 5 Гц ≈ 220 команд/с. Команды идут приоритетом VISUAL
с общим ключом на клетку, поэтому при перегрузке очередь отбрасывает
устаревшие кадры, а не важные команды.

Отдельная ловушка, которую поймал тест: снятие модели идёт приоритетом
CRITICAL, а отрисовка — VISUAL. Без общего ключа «убрать блок» обгоняло в
очереди ещё не отправленное «поставить блок», и блок оставался в мире
навсегда (NEW-01).

### 6. Управление — абсолютные цели, физика — согласованный вираж

Все значения управления (`set_target`) — абсолютные цели, физика приводит к ним
с ограниченной скоростью. Вираж считается по-настоящему: n = 1/cos(крен),
ω = g·tan(крен)/V, поэтому перегрузка и скорость разворота получаются из
крена и скорости, а не назначаются произвольно. Автопилот курса идёт в обратную
сторону: ошибка курса → желаемая ω → требуемый крен φ = atan(ω·V/g).

В наброске ручной крен и автопилот правили `self.roll` по очереди в пределах
одного тика и гасили друг друга — самолёт не выходил на курс (NEW-02).

### 7. Офлайн-разработка

`MockMCServer` реализует протокол RCON, синтетический рельеф, двигающихся
игроков и ведёт `command_log`. Тесты проверяют не только «не упало», но и
что именно ушло на сервер: сколько команд на кадр модели, не превышен ли
лимит `fill` в 32768 блоков, не задублировался ли взрыв.
