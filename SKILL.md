## 1. Протокол Source RCON (Minecraft)

### Формат пакета

```
int32  length      длина всего, что следует (включая сами эти 4 байта? — НЕТ:
                   length = размер payload = 4(id) + 4(type) + body + 2(nul))
int32  id          идентификатор запроса
int32  type        3 = AUTH, 2 = COMMAND, 0 = RESPONSE_VALUE
byte[] body        UTF-8
byte   0x00        терминатор body
byte   0x00        терминатор пакета
```

Порядок авторизации: отправить `type=3` с паролем → получить `type=2`
с тем же `id`. При неверном пароле сервер отвечает `id = -1`. Некоторые
серверы перед AUTH_RESPONSE присылают пустой RESPONSE_VALUE — читать надо
до пакета с `type=2`, а не ровно один.

### Три ловушки, которые ломают клиент

1. **Многопакетные ответы.** Ответ длиннее ~4 Кб сервер режет на несколько
   пакетов **с одним и тем же `id`**. Если прочитать один пакет и вернуть —
   остаток останется в сокете, и следующий запрос получит чужой хвост.
   Дальше поток рассинхронизирован навсегда, причём без ошибок.

   Решение (приём из библиотеки `rcon`): после команды отправить пустой
   пакет-маркер с новым `id` и читать до него, склеивая все пакеты с `id`
   команды. Реализовано в `RCONConnection._exchange`.

2. **Одно соединение — один поток.** RCON-соединение stateful: два потока,
   пишущие в один сокет, перемешивают пакеты. Round-robin «пул» этого не
   предотвращает. Решение — аренда (`lease`): соединение берётся из очереди
   и возвращается обратно.

3. **Команда длиннее 4096 байт отвергается.** Проверять до отправки, иначе
   сервер рвёт соединение. Актуально для `fill` с длинным списком или
   `summon` с большим NBT (модель из 30 блоков в одном `summon` — уже риск).

### Повторы после обрыва

Если ошибка произошла **после** отправки пакета, команду нельзя повторять:
она, скорее всего, исполнилась. Повтор = двойной взрыв или двойной спавн.
Поэтому в `_exchange` исключения помечаются флагом `_delivered`, и
`_execute` их не ретраит.

### Pipelining — главное ускорение

Minecraft обрабатывает команды последовательно, но ждать ответ на каждую не
обязательно. Можно отправить N пакетов подряд, затем пустой маркер и прочитать
N+1 ответов, сопоставляя по `id`. Выигрыш = N × RTT вместо N.

Замер: `python main.py --mock --bench`. 200 команд на localhost: 8.7 мс
поштучно против 2.4 мс пакетом — 3.7×. На удалённом сервере с RTT 40 мс
поштучная отправка тех же 200 команд — это 8 с против ~0.1 с пакетной.

### Сколько команд в секунду выдерживает сервер

Команды исполняются в серверном потоке, то есть **конкурируют с тиками мира**.
Практические ориентиры:

| Команд/с | Эффект |
|----------|--------|
| до ~100  | незаметно |
| 100–300  | лёгкие просадки TPS на слабом железе |
| 300–800  | TPS падает, лаги у игроков |
| > 800    | сервер фактически лежит |

Поэтому в `CommandQueue` стоит rate-limit (по умолчанию 250/с) и приоритеты.
Параллельные соединения TPS не спасают — узкое место сам сервер, не сеть.

## 2. Версии Minecraft и NBT

### Границы совместимости, которые важны проекту

| Версия | Что появилось | Как используем |
|--------|---------------|----------------|
| 1.13   | `execute` нового синтаксиса, `store result` | везде |
| 1.17   | `minecraft:marker` (нулевой хитбокс, без рендера) | якорь модели |
| 1.19.4 | `block_display`/`item_display`/`text_display`, `interaction`, `/damage` | backend модели `display` |
| 1.20.1 | **базовая версия проекта** | целевой синтаксис |
| 1.20.5 | команда `/ride`, компоненты предметов вместо NBT | не используем `/ride` |
| 1.21.2 | NBT сущностей переведён в snake_case (`ExplosionPower` → `explosion_power`) | `NbtDialect` |

### Два диалекта NBT

До 1.21.2 — camelCase, с 1.21.2 — snake_case. Неизвестное поле при `summon`
**молча игнорируется**, поэтому ошибка не видна: снаряд просто летит не так.
Все команды строятся через `NbtDialect` (`mc.LEGACY_NBT` / `mc.MODERN_NBT`),
никогда хардкодом.

### Определение версии без команды `version`

`version` есть только у Bukkit/Paper/Spigot. Vanilla её не имеет. Поэтому
определяем **возможности**, а не версию, — зондами на ошибку разбора:

```
execute if entity @e[type=minecraft:block_display,tag=bomber_probe_a,limit=1]
```

* тип сущности неизвестен → `Unknown or incomplete command`
* тип известен, сущности нет → `Test failed`

Зонд ничего не создаёт и не ломает (пустая выборка по несуществующему тегу).
Так же проверяется `/ride` и `/damage`. Реализовано в `mc.ServerCaps.probe`.

### `Test passed` / `Test failed`

Ответ `execute if/unless ...` — строка `Test passed` или `Test failed`.
Проверять по подстроке `pass` в нижнем регистре (устойчиво к хвостовой точке
и к лишним пробелам). Локаль сервера на это не влияет — текст всегда английский.

## 3. Приёмы в мире

### Модель техники: сущности, а не блоки

**Плохо (как в наброске):** перестраивать модель `setblock`'ами каждый тик.

* 15–20 команд на юнит на тик;
* `fill ... air` вокруг модели уничтожает ландшафт и постройки;
* если не очистить старую позицию — за юнитом тянется след из блоков.

**Хорошо:** один `minecraft:marker` как якорь + N `block_display` в пассажирах.

* движение — **одна** команда `tp` на якорь;
* смещения пассажиров заданы в `transformation.translation` и **поворачиваются
  вместе с yaw носителя** (vanilla вращает смещение пассажира на yaw носителя),
  поэтому разворот модели бесплатный;
* блоки мира не трогаются вообще — ничего не разрушается;
* `block_display` не имеет хитбокса, не падает, не рендерится лишний раз.

Посадка пассажиров на 1.20.1 (команды `/ride` ещё нет):

```
data modify entity @e[tag=root,limit=1] Passengers append value minecraft:block_display{...}
```

Работает и на 1.20.5+, поэтому единственный путь — `data modify`.

### Тангаж (pitch) модели

Yaw поворачивает пассажиров автоматически. Pitch — нет: смещения пассажиров
вращаются только по yaw. Чтобы наклонить модель, нужно либо менять
`transformation.left_rotation` (кватернион) у каждого display — дорого, либо
квантовать тангаж (например, шагом 10°) и переписывать `translation` у частей
модели только при смене бакета. Достаточно для визуала и дёшево по командам.

### «Достать игрока в пещере»

Исходная фича проекта. Ключевая команда:

```
fill x1 y1 z1 x2 y2 z2 minecraft:air destroy
```

`destroy` ломает блоки (с дропом), а не просто заменяет — полость гарантированно
открывается. Шахту от поверхности до Y игрока надо резать на куски: лимит
`fill` — 32768 блоков, поэтому один вызов на ≤ 64 блоков по Y.

Воронка от взрыва — несколько горизонтальных слоёв с радиусом
`r = sqrt(R² - dy²)` (`mc.crater`).

### Снаряды

* `fireball`: обязательно занулить `power:[0.0,0.0,0.0]`, иначе внутреннее
  ускорение уводит снаряд с вектора `Motion`. Радиус взрыва — `ExplosionPower`
  (до 1.21.2) / `explosion_power` (с 1.21.2), по умолчанию 1, с 1.21.2 — 4.
* `arrow` без `Owner` всё равно наносит урон игрокам — для «вражеского» огня
  это то, что нужно.
* Залп НАР разводится веером через смещение `Motion` (`mc.projectile_spread`).
* `direction` у `fireball` — несуществующее поле (частая ошибка из туториалов).

### Управление из игры

`scoreboard objectives add <name> trigger` → игрок пишет `/trigger <name>` →
сервер опрашивается `scoreboard players get <игрок> <name>` → после обработки
обязательно `scoreboard players set <игрок> <name> 0`.

Это единственный ванильный способ получить **действие** от игрока без предметов
и без модов. Опрос — раз в тик-интервал, не чаще.

### Позиции и углы

* `data get entity <ник> Pos` → `Name has the following entity data: [x d, y d, z d]`
* `data get entity <ник> Rotation` → `[yaw f, pitch f]`
* yaw 0 = юг (+Z), yaw 90 = запад (−X). Вектор вперёд:
  `dx = -sin(yaw)`, `dz = cos(yaw)`.
* pitch: −90 = вверх, +90 = вниз. Вертикальная составляющая `-sin(pitch)`.
* Ник в `data get entity` работает только для онлайн-игрока; для сущностей —
  селектор `@e[tag=...,limit=1]`.

### Список игроков

`list` → `There are 2 of a max of 20 players online: A, B`.
Русская локаль: `Сейчас на сервере 2 из 20 игроков: A, B`.
Парсить «всё после последнего двоеточия», разделять по запятой, срезать
` (uuid)` у вывода `list uuids`. Реализовано в `mc.parse_player_list`.

## 4. Сканер рельефа

Стоимость = (число колонок) × (запросов на колонку) × RTT. Уменьшать надо
все три множителя.

### Пакетное зондирование по уровням (главный приём)

Не вести каждую колонку сверху вниз отдельно, а спрашивать **одну высоту у
всех колонок сразу** одним `run_many`:

```
фаза A: y = 200, 184, 168, ... по всем ещё не закрытым колонкам   ~17 заходов
фаза B: бинарное уточнение внутри окна 16 блоков                  ~4 захода
фаза C: классификация по списку типов с ранним выходом            ~4-10 заходов
```

Число сетевых заходов перестаёт зависеть от числа колонок. Замер (имитатор,
localhost): 4225 колонок (r=256, шаг 8) → 67 645 команд за **544 сетевых
захода**, 1.3 с. Набросок: ~279 000 заходов на ту же область.

Команд остаётся ~16 на колонку (вместо ~66), но главный выигрыш — именно в
числе заходов: на удалённом сервере время определяет RTT, а не обработка.

### `cave_air`

`execute if block x y z minecraft:air` **не** матчит `cave_air` и `void_air`.
Пещерная полость у поверхности выглядит как «блок найден», и карта рисует
плато там, где дырка. Лечится дополнительной пробой на `cave_air` (не больше
одного лишнего запроса на колонку).

### Классификация

Пробы по списку от вероятного к редкому, с ранним выходом. Использовать
**теги блоков**, а не перечисление: `#minecraft:dirt` закрывает dirt /
grass_block / podzol / coarse_dirt одним запросом, `#minecraft:base_stone_overworld`
— все виды камня.

### Чего делать нельзя

* Многопоточное сканирование через несколько соединений: сервер исполняет
  команды в одном потоке, выигрыша нет, а гонки пула есть.
* `data get block <pos>` — возвращает NBT блочной сущности; у обычного блока
  данных нет, команда выдаёт ошибку. Узнать тип блока так нельзя.

## 5. Физика полёта

### Единицы измерения — главная ловушка

`Motion` в NBT сущности — **блоки за тик**, не за секунду. 1 блок/тик = 20 м/с.
Если задать `Motion:[2.5,0,0]`, снаряд полетит со скоростью 50 м/с. Все
каталожные скорости в проекте указаны в блоках/тик, а для баллистики есть
`speed_mps()`.

Эффективная гравитация сущностей Minecraft ≈ **15-16 м/с²** (0.04 блока/тик²
плюс drag 0.98), то есть вдвое меньше реальной. Время падения бомбы со 100 м —
около 3.6 с, упреждение при 20 м/с — около 70 блоков. Без упреждения
бомбометание бессмысленно.

`fuse` у TNT — в **тиках** (20/с).

### Согласованный вираж

Перегрузка и скорость разворота не назначаются, а выводятся из крена:

```
n = 1 / cos(φ)              перегрузка
ω = g · tan(φ) / V          рад/с, g ≈ 15 м/с²
φ_max = acos(1 / n_max)     крен, соответствующий пределу по G
```

Отсюда же ограничение по паспорту планера: если `n > max_g`, крен урезается до
`φ_max`. Для Су-25 (4.5g) это ±77°, для Ту-95 (2.5g) — ±66°.

### Автопилот курса — в обратную сторону

Пропорциональный регулятор «крен = ошибка × k» раскачивается и не сходится:
при большой ошибке крен упирается в предел, самолёт проскакивает курс, и
начинаются незатухающие колебания. Рабочая схема — через желаемую угловую
скорость:

```
ω_des = clamp(ошибка_курса × gain, -ω_max, +ω_max)     град/с
φ_des = atan(ω_des · V / g)                            требуемый крен
```

Сходится без подбора демпфирования: при ошибке → 0 желаемый крен тоже → 0.
Ошибка удержания курса на Су-25 — ±4.5°.

**И критично:** целевое положение рулей должно вычисляться в ОДНОМ месте и
применяться один раз за тик. Если ручной крен и автопилот правят `self.roll`
по очереди, они гасят друг друга, и крен застревает на промежуточном значении
(в нашем случае −5.5° при требуемых −55°).

### Сваливание

Три составляющие, иначе это не сваливание, а просто флаг:

1. потеря эффективности рулей (`authority ≈ 0.35`);
2. растущая скорость снижения: `sink = 4 + (V_stall − V) × 1.5`;
3. самопроизвольное опускание носа (`pitch → +12°`) — именно оно даёт вывод.

И обязательное условие: **целевая скорость на малом газу должна быть НИЖЕ
скорости сваливания**. Если принять её равной `min_speed`, самолёт с убранным
газом будет разгоняться и не свалится никогда. В проекте
`idle_speed = 0.6 × stall_speed`.

### Вертолёт

Отдельная схема, а не «самолёт с нулевой минимальной скоростью»:

* РУВ (`throttle`) → вертикальная скорость: `vy = (throttle − hover) × 2 × climb_rate`;
* циклический шаг → горизонтальная: продольная от тангажа, поперечная от крена;
* рысканье — напрямую `yaw_rate`, без крена.

Расход топлива в висении не должен быть нулевым — несущий винт работает.

## 6. Блочная модель

### Считать каждый свой блок

Единственный способ рисовать технику блоками, не разрушая мир: модель хранит
`{(x,y,z): block}` — ровно то, что поставила сама. Тогда:

* `clears` = клетки, которых больше нет; `writes` = новые или изменившиеся;
* уборка — `setblock x y z minecraft:air` **только по своим координатам**;
* никогда не использовать `fill ... air` вокруг модели: он стирает ландшафт
  и постройки.

### Дифф, а не перерисовка

При движении на 1 блок меняется часть клеток, а не все. При повторе той же позы
дифф пуст — ноль команд. Ключ кадра имеет смысл квантовать в целые блоки и
бакеты по 4°: раскладка клеток всё равно целочисленная.

### Бюджет команд

```
команд/с ≈ 2 × N_блоков × частота_обновления   (на движущийся юнит)
```

Су-25 (22 блока) при 5 Гц ≈ 220 команд/с — впритык к безопасному пределу
250/с. При 12 Гц было бы 530 — сервер бы лёг. Поэтому частота перерисовки
модели задаётся отдельно от частоты физического тика.

### Инверсия приоритетов — неочевидная ловушка

Снятие модели логично делать приоритетом CRITICAL (важнее визуала), а отрисовку
— VISUAL. Но очередь сортирует по приоритету, поэтому «убрать блок» обгоняет
ещё не отправленное «поставить блок» для той же клетки — и блок остаётся в мире
навсегда. Лечится **общим ключом слияния на клетку** для записи и стирания:
тогда новая команда вытесняет старую независимо от приоритета.

## 7. Маршруты и ИИ

### Достижение точки: радиус не работает на скорости

Окно фиксированного радиуса (`dist <= 3`) физически недостижимо: самолёт на
60 м/с при тике 0.5 с пролетает 30 блоков за тик и «перешагивает» точку.
Маршрут не выполняется вообще, причём без единой ошибки.

Правильная проверка — **пересечение плоскости точки**:

```
d = cur - prev                       # вектор движения за тик
to_wp = wp - cur
along = dot(to_wp, d) / |d|          # проекция на направление движения
пролетели, если along <= 0
```

Работает при любой скорости и любом тике. Дополнительно радиус точки надо
брать не меньше пути за тик: `radius >= max_speed × dt`, иначе проверка
`dist <= radius` не сработает между кадрами.

Для вертолёта, БПЛА и танка естественен второй режим — точный выход в радиус,
но с **отдельным и более мягким допуском по высоте**: вертолёт снижается
медленно, и требование «Δвысоты ≤ 8 м» недостижимо.

Обязателен предохранитель по таймауту: точка, до которой юнит не дошёл
(снесло ветром, застрял в рельефе), помечается пропущенной, и маршрут идёт
дальше. Без этого любой сбой означает вечное зависание.

### Действия выполняются ДО точки, а не после

Бомба падает t = √(2h/g) секунд и уходит вперёд на V·t. При 37 м/с и высоте
90 м это ~128 блоков. Значит сбрасывать надо **за 128 блоков до цели**, а не
в момент пролёта. То же для УР (пуск на 85% дальности) и обстрела (вход в зону
огня заранее).

Отсюда важное следствие: высота ЦЕЛИ — это не высота полёта юнита. Если
целиться в `waypoint.altitude`, высота падения окажется нулевой, дистанция
сброса — тоже, и бомбы лягут позади цели. Цель берётся из рельефа под точкой
(`target_altitude`), либо из позиции названного игрока.

### Управление вертолётом ≠ управление самолётом

У вертолётных тангаж — это **поступательное** движение, а вертикаль задаётся
общим шагом (РУВ). Если использовать тангаж для набора высоты (как для
самолёта), вертолёт вместо набора улетает вперёд и никогда не выходит в точку.

Разделение:
* самолёт: курс — автопилотом по крену, высота — тангажом, скорость — тягой;
* вертолёт: курс — рысканьем, горизонталь — тангажом/креном, вертикаль — шагом.

### Перепланирование ИИ: только по событию

Пересчёт маршрута КАЖДЫЙ тик ломает исполнение: новый маршрут приходит с
`current_idx = 0`, и юнит вечно летит к первой точке. Рабочая схема — гибрид:

```
пересчитать, если  цель сдвинулась > порога
                ИЛИ истёк интервал (2 с)
                ИЛИ текущий маршрут завершён
```

И при пересчёте точки заменяются **на месте** (`replace_waypoints`), с
сохранением `current_idx` и флагов пройденных. Между пересчётами ИИ возвращает
`None` — маршрут не трогается.

### Заход на цель

Направление захода — от цели к юниту (минимальный разворот). Особый случай:
юнит уже над целью (ближе 40 блоков). Тогда рубеж ставится **впереди по курсу**,
а не позади: самолёт пролетает вперёд, доворачивает и возвращается на цель.
Рубеж позади заставлял бы его развернуться на 180° и проскочить цель.

### Rate-limit обязан быть общим

Ограничитель скорости очереди, повешенный на каждого воркера, даёт `N × rate`.
При двух воркерах и лимите 250/с фактически уходило 463/с — сервер лёг бы.
Нужен один общий «следующий разрешённый момент» под блокировкой, с ограничением
накопленного долга (иначе всплеск останавливает очередь надолго).

## 8. Архитектура и потоки

### Правило: ядро не знает про Qt

Ядро публикует события в `EventBus`, UI подписывается и **сам** маршалит их в
GUI-поток (в Qt — через `Signal`, который при кросс-поточной доставке работает
как очередь). Прямые вызовы методов виджетов из фоновых потоков запрещены:
это падение в произвольный момент, которое почти невозможно воспроизвести.

### Правило: `snapshot()` возвращает копии

UI держит снимок и может перебирать его, пока физический поток меняет объект.
Любая возвращаемая изменяемая структура копируется. Контракт зафиксирован
тестом `test_snapshot_survives_concurrent_route_mutation`.

### Правило: id присваивается до возврата из `add_unit`

Поток юнита не должен регистрировать сам себя в мире: вызывающая сторона
получает `None` в качестве id и теряет юнит. Регистрация — синхронно, до
`thread.start()`.

### Правило: тяжёлое — в очередь, лёгкое — сразу

Всё, что уходит на сервер, проходит через `CommandQueue` с приоритетами:

| Приоритет | Что | Поведение при перегрузке |
|-----------|-----|--------------------------|
| `CRITICAL` (0) | взрывы, спавн, удаление | не выбрасывается никогда |
| `NORMAL` (10)  | выстрелы, tp, служебное | не выбрасывается |
| `VISUAL` (20)  | кадры модели | сливается по ключу, выбрасывается первым |

Слияние по ключу: `submit(cmd, VISUAL, key='model:3')`. Если предыдущий кадр
этого же юнита ещё не отправлен, он помечается отменённым — рисовать
промежуточные кадры всё равно никто не увидит. На 40 кадров модели в очередь
уходит 1 команда.

### Горячие клавиши

`QShortcut(QKeySequence("W"), self)` на уровне окна перехватывает W везде,
включая `QLineEdit` — в поле ника невозможно ввести «W». Нужно либо
`Qt.WidgetWithChildrenShortcut` на конкретном виджете карты, либо проверка
`isinstance(QApplication.focusWidget(), QLineEdit)` в обработчике.

### Рендер карты

Пересоздавать `QGraphicsItem` для каждого тайла каждый кадр — гарантированный
фриз на 10 000 тайлов. Правильно:

* статичное (рельеф, сетка) → один `QPixmap`-фон, перерисовывается только при
  изменении рельефа/зума/панорамы;
* динамическое (юниты, маршруты, игроки, маркеры) → отдельные item'ы, их
  десятки, не тысячи;
* координаты клика → `mapToScene(event.position().toPoint())`, никогда не
  `event.position()` напрямую.

## 9. Соглашения кода

* Язык интерфейса, комментариев и сообщений — русский. Идентификаторы — латиница.
* Все строковые команды Minecraft собираются в `mc.py` и возвращают `str`.
  Отправка — только через `rcon.CommandQueue` / `RCONPool`. Так команды можно
  тестировать сравнением строк без сервера.
* Конфигурация — только `AppConfig` (`config.py`), никаких констант в теле
  модулей. Переопределяется файлом `bomber.json` и переменными
  `BOMBER_HOST/PORT/PASSWORD/MOCK/TICK`.
* Каждая единица техники обязана реализовать контракт:
  `step(dt, world)`, `snapshot()`, `build_model()/clear_model()` (или
  стратегию модели), поля `fuel_left`, `ammo` — чтобы общий код не проверял
  их наличие через `hasattr`.
* Тесты — `unittest` (stdlib), запуск `python main.py --selftest` или
  `python -m unittest discover -s tests -t .`. Никаких внешних зависимостей
  у тестов: сервер имитируется `mock_server.MockMCServer`, а очередь команд —
  регистратором `FakeQueue`, чтобы проверять сами строки команд.
* Таймеры внутри симуляции — в **секундах симуляции**, не настенных: пауза
  обязана останавливать и ракеты, и отложенные взрывы.
* Новый фикс → строка в `BUGS.md` (статус `✅`) + тест. Без теста статус не
  меняется.

## 10. Как отлаживать без Minecraft

```bash
python main.py --mock              # весь тракт на имитаторе
python main.py --flight            # спавн, полёт по курсам, огонь, деспаун
python main.py --mission 40        # маршруты, ИИ по фазам, библиотека JSON
python main.py --mock --scan 128 8 # рельеф + ASCII-карта
python main.py --mock --watch 10   # движение игроков
python main.py --mock --bench      # пакетная vs поштучная отправка
python main.py --selftest          # 74 теста
python main.py --probe             # только зонд возможностей
```

`MockMCServer` ведёт `command_log` — список всех полученных команд. Это
позволяет проверять не только «не упало ли», но и **что именно** ушло на
сервер: сколько команд на кадр модели, не превышен ли лимит `fill`, не
дублируется ли взрыв. Примеры — в `tests/test_rcon.py::test_merging_stale_visual_commands`.

Имитатор держит синтетический рельеф (`ground_height`, `top_y`, `surface_kind`)
и двигающихся игроков, поэтому сканер, трекер и будущий ИИ тестируются
детерминированно.


## 11. Силуэты и LOD на тактической карте
* Силуэт задаётся в локальных координатах (вправо, вперёд) и поворачивается по
  yaw одним преобразованием; симметрия вида сверху проверяется тестом
  (множество X-координат зеркально относительно оси).
* LOD: иконка держит физический габарит (~14 м), но не меньше читаемого min_px —
  знак не должен исчезать в точку. «Тяжесть» при отдалении передаётся
  прозрачностью и упрощением (лопасти -> подписи -> винт), а не размером.
* Несущий винт вертолёта: ометаемый диск (пунктир) на среднем LOD, лопасти с
  фазой вращения — на крупном; фаза крутится только в полёте.

## 12. Боевая модель
* Урон централизован в `Unit.take_damage`; броня гасит фиксированный процент
  (до 80%). Все источники (бомба/НАР/пуля/ракета/игрок) идут через неё —
  поражение одинаковое и тестируемое.
* Взрыв: урон с фолл-оффом по дистанции и `skip` инициатора, чтобы бомба не
  сбивала собственный носитель. Прямой урон (пули/НАР) откладывается на время
  полёта снаряда до цели.
* Огонь из игры — через scoreboard-триггер (`/trigger bomber_fire`): поллер
  читает счёт игрока, сбрасывает и бьёт ближайшего врага в конусе взгляда.
  Это ванильный механизм без модов.

## 13. Базы и блочные ракеты
* База = точка + ориентация + стоянки (pads) + услуги. Стоянка задаёт точку и
  курс взлёта; занятость видна на карте и в панели запуска.
* Блочная ракета переиспользует механику модели техники (`BlockModel` + дифф),
  поэтому в полёте видна цепочкой блоков и на карте силуэтом; детонация идёт
  через CombatSystem, блоки убираются при попадании/самоликвидации.

## 12. Dear PyGui 2.3.1: подводные камни (порт UI, итерация 4)

* **Тема**: `add_theme_color`/`add_theme_style` кладутся ТОЛЬКО в
  `add_theme_component(parent=theme)`. Передача `parent=theme` → ошибка
  1003 «Incompatible parent»; если её проглотить, интерфейс молча остаётся
  дефолтным. Векторные стили — двумя позиционными `(x, y)`.
* **Контейнеры**: `dpg.last_container()` = последний созданный контейнер
  (drawlist считается!), а не вершина `with`-стека. Родителей холстов
  держим явно (`with dpg.group() as g:`).
* **Рисование**: `add_drawlist` (не `add_drawing`); `draw_polygon` замыкает
  контур всегда — для дуг/шевронов `draw_polyline(closed=False)`;
  `draw_text` не принимает шрифт и не вращается; форматы текстур только
  Float_rgb/Float_rgba.
* **Мышь**: move/wheel/release существуют только в глобальном
  `handler_registry` → каждый хендлер сам проверяет «курсор над пером»;
  клики — `item_handler_registry`, привязанный к item (перо, холст иконки).
* **Геометрия**: `get_item_rect_*` валидны только после первого рендера;
  client-размер вьюпорта на переходных кадрах промежуточный → раскладку
  пересчитываем и по resize-колбэку, и периодически (каждые 30 кадров).
* **Шрифты**: регистр обязателен (`font_registry`); кириллица есть в
  DejaVuSans/Mono (бандлим Mono + Mono-Bold); `bind_item_font` даёт
  иерархию веса (bold-заголовки). Иконочные гарнитуры не сливаются с
  текстовой → иконки рисуем вектором (`rwf/uicons.py`, сетка Lucide 24×24).
* **Секции доков**: `collapsing_header` не стилизуется до «тактического»
  вида — собственный холст-заголовок (шеврон+иконка+линия) с кликом через
  item-хендлер и телом в `group(show=...)`.
* **Журнал**: автопрокрутка child-окна ненадёжна — новые записи сверху.

## 14. v14: хотбар, контекстное меню, таблицы (второе ревью)

* **Хотбар** — только маршрутные инструменты, слева, иконки без подписей,
  скрываемый (`state["hotbar"]`, `layout()` пересчитывает карту). Команды
  уровня «миссия» (скан/стоп/сброс/выход) живут в секциях и ПКМ-меню.
* **Контекстное меню ПКМ** (`ui/context.py`): одно окно `win_ctx` с пулом
  кнопок (I2); наполнение по хит-тесту (юнит/база/игрок/пусто); закрытие —
  клик вне (проверяется в глобальном mouse-release карты), ПКМ или пункт.
  Колбэки пунктов — только `facade.send`/мутации STATE (I1/I4).
* **Таблицы DPG**: `add_table` + `add_table_row`; клик по строке — через
  `add_selectable` в ячейках (у `mvTableRow` нет click-хендлеров!), иконки —
  drawlist в первой ячейке; подсветка выбора — `set_table_row_color`
  (цвет текста selectable не конфигурируется). `add_text` в DPG 2.x не
  имеет width — колонки вне таблиц делает обёртка `build.tcol`.
* **Пульт любого объекта**: `state["console_obj"]` = ("unit",uid)|
  ("player",name)|("base",id); проекция строит карточку по типу, силуэт —
  тем же `icons.unit_icon` (LOD detail=2), бар груза только при cargo_max>0.
* **Звук и настройки**: `sound.py`/`settings.py` вне UI-пакета (тестируются
  без GL); UI лишь проецирует виджеты секции «НАСТРОЙКИ» в Settings.
* **Диалог запуска**: Tkinter ДО `create_context()` DPG — два GUI-контекста
  в одном процессе невозможны; скриншоты/CI идут с `--no-dialog`.

## 15. v15: раскладка без верхней полосы, пресеты, экономика, разрушения

* **Статус-строка живёт в заголовке окна карты.** Отдельное окно-полоса
  съедает высоту и выглядит пустой; `configure_item(win_map, label=...)`
  обновляется за микросекунды и не плодит виджеты. Держи текст за подписью
  (`sig`), иначе каждый кадр дёргает ImGui перерисовкой заголовка.
* **Левая колонка объекта = ширина силуэта.** Панель, которую хочется
  «уменьшить», проектируй от размера картинки: OBJ_W = силуэт + поля, всё
  остальное (таблицы, бары, сетка кнопок) подстраивается. Адаптивный набор
  строк параметров по типу машины важнее универсальной таблицы: пустые
  строки читаются как баг.
* **Числа не кладут внутрь ярких полос.** Overlay DPG-бара наследует цвет
  текста темы и непредсказуем на светлом fill'е; значение печатай рядом
  отдельным текстом на тёмной подложке.
* **Тултипы вместо подписей, но только на листовых виджетах.** Контейнер
  (таблица/строка/окно) в качестве родителя `add_tooltip` роняет процесс;
  `dpg.tooltip(...)` как контекст-менеджер ломает стек контейнеров. Подсказки
  таблиц вешай на заголовок секции или иконки строк.
* **Пресеты = файл на рецепт.** Экран запуска держит четыре выбора
  (тип → пресет → база → старт), а ручная сборка уходит в модальное окно.
  Перетаскивание: payload ребёнком источника (`drag_data`), приём через
  `drop_callback`; всегда имей клик-путь как запасной — drag&drop не проверить
  в headless-кадре.
* **Экономика делает услугу дефицитом, а не декорацией.** Очки копятся,
  имеют неснижаемый остаток и списываются пропорционально недостающему
  топливу/боезапасу/прочности; при дефиците услуга частичная и помеченная.
  База без регенерации (авианосец) оживает только через логистику: груз
  транспортника → очки снабжения при посадке.
* **След аварии обязан переживать юнит.** Кратер + остов (чертёж юнита,
  детерминированно разваленный по uid) + падающие обломки + огонь с
  автогашением. Контракт тестов: блоки МОДЕЛИ убраны, в мире остались только
  клетки зарегистрированного сайта — иначе «чужие» блоки считаются утечкой.
* **Наземная коллизия считается по тайлу назначения, уклон — по шагу тайла.**
  Проба «вперёд» обязана сменить тайл (четверти шага), иначе банковское
  округление оставит её под ногами и стена станет невидимой. Дорога дешевле
  пересечёнки и в стоимости клетки, и в скорости — тогда автопилот сам
  выходит на дороги без отдельного pathfinding'а.
* **Прогрессия считает результат, а не активность.** Очки за сбитое/посаженное/
  доставленное/снесённое, штраф за потерю своей машины; события приходят
  шиной, модуль не трогает тик. Звание и достижения переживают сессию.
